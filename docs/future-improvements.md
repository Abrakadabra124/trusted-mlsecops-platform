# Будущие улучшения после R1

Постоянный backlog, зафиксирован 2026-10-20. [Границы R1 и обязательные блокеры](r1-delivery.md) имеют приоритет. Пункты ниже не выполняются автоматически; новый пункт не меняет scope R1. Допустимые статусы: `planned`, `in_progress`, `done`, `rejected`. ID не переиспользуются; при отказе сохраняются причина и статус.

P1 - первый кандидат после выполненных зависимостей; P2 - после P1; P3 - отдельная инициатива. Размер - приблизительные инженерные дни исследования, реализации и проверки без закупок/внешнего согласования: S 1-2, M 3-5, L 6-10, XL требует отдельной оценки. Эти размеры не обещают production readiness.

## FI-001: независимые failure domains и offsite recovery

- **Проблема / польза:** один host не переживает собственную потерю; независимый backup/failure domain уменьшит blast radius.
- **Основание:** обнаруженное ограничение lab, описанное в baseline gap и M17; не доказанный production incident.
- **Почему отложено:** R1 требует независимый restore в новом lab storage и измеренный RTO/RPO, но не multi-node HA/offsite. Сам M17 остаётся R1-B06.
- **Приоритет / размер:** P1 / XL. **Зависимости:** R1 принят, бюджет, target topology и владельцы recovery согласованы.
- **Готовность / проверка:** исходный failure domain недоступен, восстановление в другом проходит digest/golden checks и согласованные RTO/RPO; протокол game day.
- **Статус:** planned.

## FI-002: production identities и аппаратно защищённые ключи

- **Проблема / польза:** host administrator контролирует lab keys; KMS/HSM и независимые роли сократят этот риск.
- **Основание:** явная trust-boundary limitation GOAL; не утверждение об уже скомпрометированных ключах.
- **Почему отложено:** R1 использует раздельные lab identities и проверенные signatures. Их проверка и исправление текущих release blockers не откладываются.
- **Приоритет / размер:** P1 / XL. **Зависимости:** R1, выбранный provider, budget, владельцы signer/approver и production threat model.
- **Готовность / проверка:** documented key lifecycle/rotation/revocation; workload не извлекает private key; negative role/sign/replay tests и восстановление доступа.
- **Статус:** planned.

## FI-003: внешняя SIEM-интеграция и Sigma backend

- **Проблема / польза:** встроенный lab alert route не интегрирован с действующим SOC; адаптер объединит расследования.
- **Основание:** условная интеграция в M23, конкретный backend пока не выбран.
- **Почему отложено:** M23 требует реальные events/delivery/dedup/gaps, но Sigma deployment только при выбранном backend. Эти базовые проверки остаются R1-B05.
- **Приоритет / размер:** P2 / M. **Зависимости:** M23, согласованные backend/schema/auth/retention и доступ.
- **Готовность / проверка:** 7 event types сохраняют смысл, повторный replay не дублирует incident; mapping/deny/outage tests и private-data scan.
- **Статус:** planned.

## FI-004: операторский интерфейс

- **Проблема / польза:** работа через CLI/файлы требует знания структуры; UI покажет candidate, причины запрета, metrics и recovery actions.
- **Основание:** гипотеза удобства, не доказанный blocker.
- **Почему отложено:** R1 принимается по воспроизводимому CLI/API и ранбукам; интерфейс не заменяет их.
- **Приоритет / размер:** P2 / L. **Зависимости:** R1, стабильные API/schema и пользовательские сценарии.
- **Готовность / проверка:** operator выполняет approved/denied/revoke/restore сценарии; backend policy невозможно обойти через UI; usability и authorization tests.
- **Статус:** planned.

## FI-005: производительность сверх обязательного lab SLO

- **Проблема / польза:** ограничения одного CPU и синхронного inference могут мешать будущему масштабу; измеренная оптимизация увеличит throughput.
- **Основание:** гипотеза до профилирования. Текущее прохождение M14 не подтверждено.
- **Почему отложено:** обязательные p95/p99, error rate и overload по M14 остаются R1-B06; сюда относится только улучшение сверх них.
- **Приоритет / размер:** P2 / M после измерения. **Зависимости:** M14 pass, профиль workload и найденное bottleneck.
- **Готовность / проверка:** before/after на одинаковых inputs/resources, статистически объяснимый выигрыш без ухудшения correctness/privacy/security; без неподтверждённых процентов.
- **Статус:** planned.

## FI-006: долговременное forensic-хранилище приватных доказательств

- **Проблема / польза:** CI packet исчезает при уничтожении VM; отдельное encrypted storage позволит расследование позднее.
- **Основание:** обнаруженный lifecycle факт ADR0049; хранение identifiers создаёт дополнительный privacy risk.
- **Почему отложено:** этот пункт про production off-host preservation. Обязательные lab retention/expiry, доступность evidence для M18, backup/restore и публичная редакция остаются R1-B06/B08.
- **Приоритет / размер:** P2 / L. **Зависимости:** R1, purpose/retention/privacy approval, encryption/key owners и бюджет хранения.
- **Готовность / проверка:** authorized retrieval после потери VM; integrity, deny/access audit, expiry/legal-hold policy и restore drill без публикации private payload.
- **Статус:** planned.

## FI-007: новые модели исполнения и AI-сценарии

- **Проблема / польза:** CPU tabular профиль не покрывает GPU/ARM/distributed training, LLM/RAG/агентов; отдельные профили расширят применимость.
- **Основание:** явный out-of-scope GOAL, не требование существующего продукта.
- **Почему отложено:** другой runtime, threat model, ресурсы и критерии. Исправления текущего CPU candidate не относятся к этому FI.
- **Приоритет / размер:** P3 / XL. **Зависимости:** R1, конкретный use case, бюджет и отдельная утверждённая спецификация.
- **Готовность / проверка:** отдельный compute/security profile и воспроизведение его positive/negative acceptance; не переносить CPU/privacy claims автоматически.
- **Статус:** planned.

## FI-008: исследования membership inference и differential privacy

- **Проблема / польза:** отсутствие raw features в логах не исключает утечку через модель; исследование определит остаточный риск для выбранных данных.
- **Основание:** известная граница M13, без заявления о конкретной найденной атаке на lab.
- **Почему отложено:** R1 synthetic-only и не обещает DP. Canary/privacy/audit controls и реальные обнаруженные утечки остаются обязательными.
- **Приоритет / размер:** P3 / XL. **Зависимости:** R1, законный dataset, threat model и независимый privacy review.
- **Готовность / проверка:** заранее заданный attack protocol; при выборе DP определены privacy unit, adjacency, epsilon/delta, composition, utility trade-off и проверка реализации.
- **Статус:** planned.

## Порядок продолжения

После приёмки R1 показать очередь, но не запускать её. По явной команде владельца выбирать следующий приоритетный FI с выполненными зависимостями; если их нет, назвать недостающие условия. Перед реализацией изменить статус на in_progress, после проверки - done со ссылкой на evidence; не удалять неудачные результаты.
