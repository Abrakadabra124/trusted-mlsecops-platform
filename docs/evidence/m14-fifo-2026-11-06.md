# M14: FIFO и повторная проверка клиентских TLS-файлов

Два отдельных hosted запуска на фиксированном профиле [M14](../acceptance.md#m14):
10 s warmup, 120 s measurement, 10 клиентов, одна golden row, новый TCP на запрос.
Оба полностью измерены, но **fail по p95; полный M14 и R1 не приняты**.
Qualification permit не разрешает production release.

Клиентское окно полностью наблюдалось и не достигало cap. CPU считается по
реальным границам counters, не ровно по 120 s; summary timestamps имеют
разрешение 1 s. Sampled memory не доказывает настоящий peak. Контейнеры, лимиты,
golden validation, trust checks и overload profile не изменены.

FIFO уменьшил наблюдаемый хвост, но throughput этого запуска ниже. Это по одному
запуску на commit, без заявления о статистической значимости. `engine_wait`
после FIFO не включает HTTP queue; для сравнения используются полные client-side
latencies. Порядок и ownership описаны в [ADR 0056](../decisions/0056-load-measurement-profile.md).

Диагностика `506a762`: 25834 `connection_parameters` вызова заняли 47.660 s,
12917 `session_credentials` - 37.959 s; эти интервалы вложены, их нельзя складывать.
Engine удерживался 125.980 s за 6445 операций во всех фазах опыта. Source inspection
подтвердил повторную полную валидацию перед входом в Session и внутри неё.
Следующий эксперимент убирает внешний повтор только у управляемой Session;
это гипотеза ускорения, а не успешный результат данного отчёта.

До shutdown audit оставался healthy: `df7ff2f` accepted=30056/durable=30055/pending=1,
`506a762` accepted=25768/durable=25766/pending=2, unconfirmed=0. Это снимки до close,
не доказательство, что все записи уже durable в момент снимка. Последующий shutdown
прошёл явную проверку Uvicorn lifespan flags, worker cleanup и повторное чтение
operator packets. Tmpfs журнала не обеспечивает сохранность после удаления Pod.
