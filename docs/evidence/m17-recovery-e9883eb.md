## Что произошло на стенде

1. Workflow собрал закреплённый CPU-образ, подготовил данные, обучил и оценил модель. Зафиксировал исходные идентификаторы датасета, оценки, предложения выпуска и публичных ключей.
2. В исходной базе созданы два контролируемых подписанных решения для тех же байтов модели. Системный таймер запустил штатную службу копирования в 01:32:28,914489 UTC. Служба завершилась с кодом 0 и сохранила идентификатор снимка отдельно от архивов. Следующим календарным сроком systemd указал 02:00 UTC того же дня.
3. Исходная база остановлена. Восстановление прочитало ровно этот архив в новый PostgreSQL с отдельными томом, сетью и TLS-учётными данными. Из target проверены подписанная оценка, предложение выпуска, журнал разрешений и прогнозы. Обычная проверка полномочий сохранила отказ в выпуске исходного предложения. Контролируемый выпуск позволил проверить работающий HTTP-путь и отказ после отзыва ключа.
4. Операторский CLI повторно проверил исходные хеши, подписи, внешний инвентарь, обе мутации исходного архива, результаты HTTP-проб и часовую шкалу после остановки source и target. Проверен SHA-256 канонического публичного отчёта, извлечённого из опубликованного лога.

## Воспроизведение и границы

На Ubuntu прошли 74 теста. В независимом чистом checkout Windows с Python 3.12.15 повторены те же 74 теста. В восьми измеренных модулях покрыты 945 из 945 исполняемых строк и 156 из 156 ветвей. Без материалов попытки обычный CLI на Windows возвращает `inconclusive` и код 2. [Операторские команды и плейбук](../operations/storage-recovery-acceptance.md).

Это один отказ на одном одноразовом хосте. Календарь проверен с ускоренным срабатыванием. Для оценки фактической суточной периодичности нужны наблюдения на постоянно работающем хосте. Восстановление на другой площадке, высокая доступность и допуск исходного предложения к эксплуатации остаются за пределами этого измерения.
