# Приватные release assets одного публичного запуска

Интерфейс [адаптера](../../scripts/ci_private_assets.py) для доверенного
контроллера CI (continuous integration). Оператор отвечает за приватный
репозиторий и терминальное разрешение. Producer передаёт четыре существующих
шифрованных пакета. `expected` поступает от публичного workflow и содержит
ровно `repository, run_id, run_attempt, source_revision, producer_job`.
ID и attempt являются положительными целыми, source_revision содержит полные
40 строчных hex-символов. Пример последовательности в памяти процесса:

```python
receipt = publish(writer, expected, packets, seal_control, checkpoint=save_private)
encrypted_control = fetch_control(reader, expected)
signed_receipt = open_and_verify_control(encrypted_control, producer_public_key, expected)
candidate = fetch(reader, expected, signed_receipt, "candidate-shared")
cleanup(writer, expected, receipt, authorize=terminal_decision, retained_copy=read_retained)
```

`packets` содержит ровно четыре stem: `candidate-shared`, `candidate-serving`,
`upstream-serving`, `validation-serving`. Файлы имеют суффикс `.bin`.
`seal_control(receipt) -> bytes` получает независимые ID и хэши после реального
чтения каждого пакета. Producer подписывает эту квитанцию вместе с исходными
контекстами и шифрует результат. Пятый файл `producer-control.bin` имеет
префикс `MLSCONTROL\x01`, 12-byte nonce и ciphertext с 16-byte tag, до 65536
байт включительно. Публичный ключ подписи допускается передать через
`needs.producer.outputs`. Хэши, ID, квитанции и зашифрованные байты остаются
в приватном контуре. Проверка подписи, AEAD (authenticated encryption with
associated data) и исходных окон выполняется вызывающим кодом.

Формат квитанции содержит `schema_version, expected, repository_id, tag,
private_head, release_id, issued_at, expires_at, assets`. Значения в `assets`
индексируются по stem, поля каждого значения: `id, size, sha256`.
Подписанный снимок охватывает четыре пакета. Возвращаемая `publish` полная
квитанция охватывает также пятый файл. Сохранение квитанции для cleanup
выполняется независимо в доверенном приватном хранилище.
`producer_receipt(receipt, expected)` проверяет закрытую схему четырёх строк,
тип каждого ID, уникальность ID, размеры, namespace и окно. Возвращает
отдельную копию для подписи или после проверки подписи. Каждый `fetch`
повторно проверяет доверенную квитанцию и сопоставляет её с текущим release.

## Предварительные условия

Использовать разные repository-scoped credentials на
`Abrakadabra124/trusted-mlsecops-ci-private`. Publisher и терминальный
оператор требуют Contents write, consumer требует Contents read.
Публичный workflow независимо проверяет источник, job `producer`, run и
attempt по фактическим данным Actions. Repo ID приватного хранилища
`1465012664` проверяется вместе с точным регистром owner/full_name, признаками
`private=true`, `visibility=private`, `fork=false`. Значения token/key в
аргументах команд, URL, диагностике и публичных outputs недопустимы.

Оператор сериализует писателей этого namespace на всё время публикации и
очистки, включая повторы после сбоя. Получатель имеет только чтение.
Терминальный оператор закрывает attempt для повторной публикации во внешнем
контроллере. После удаления тега и release GitHub не хранит в этом интерфейсе
маркер использованного namespace. Повторный запуск producer получает новый
attempt. Администраторы репозитория и GitHub входят в границу доверия.
REST API не предоставляет здесь атомарной операции «удалить release, только
если он всё ещё пуст», а удаление ref не принимает ожидаемый старый SHA.
Одновременный посторонний writer нарушает предпосылку безопасной очистки.

## Публикация и чтение

1. Вызвать `publish` с уже запечатанными пакетами. Обработчик проверяет
   префикс AES-конверта и границы длины каждого файла до резервирования тега.
   Верхние границы в байтах составляют 83 886 115 для каждого candidate,
   89 544 059 для upstream, 22 435 195 для validation и 65 536 для control.
   Всего до 279 817 020 байт в одном release. Подлинность содержимого
   устанавливают криптографические readers.
2. Адаптер читает default branch из приватных metadata и полный SHA через
   `git/ref/heads/{default_branch}`. Он проверяет отсутствие тега, release и
   совпадающих черновиков. Просмотр ограничен 20 строками, до создания
   допускается максимум 18 существующих releases. Читающий токен для
   preflight публикации должен видеть черновики. Создание lightweight tag
   `ci-candidate-{run_id}-{run_attempt}` выполняется только через create.
   При конфликте операция завершается. Новый prerelease привязан к этому
   точному SHA, имеет `make_latest=false` и доступен reader. Описание
   связывает release с ожиданиями публичного запуска. Адаптер записывает
   каждый файл один раз. Подмену файла reader выявляет по подписанным ID,
   размерам и SHA-256.
   Профиль GitHub с включённой immutable release policy несовместим с
   поэтапной загрузкой и терминальным удалением по этой процедуре.
3. После каждого подтверждённого создания tag, release или asset
   `checkpoint(receipt)` получает независимый снимок. Для межпроцессного
   восстановления сохранять снимки атомарно в защищённом приватном журнале
   оператора. Запись файла с квитанцией имеет те же требования к доступу,
   что и сами пакеты. При ошибке записи операция останавливается.
4. После upload адаптер проверяет точные metadata и повторно скачивает байты
   по числовому ID. Control создаётся последним. Reader получает его по
   детерминированному тегу после проверки release по ID и полного списка
   пяти файлов. `fetch_control` возвращает байты для проверки подписи.
   При чтении пакета только независимая подписанная квитанция задаёт
   ожидаемый ID, SHA-256 и размер. Для чтения до и после I/O действует окно
   `issued_at <= now < issued_at + 1800` секунд. Исходный срок proposal и
   требования каждого потребителя проверяются отдельно.

## Терминальная очистка и восстановление

Внешний контроллер проверяет фактическое завершение jobs, захватывает право
на эксклюзивную очистку и передаёт приватную квитанцию из журнала.
`authorize(receipt)` получает её копию и возвращает закрытый словарь:

```python
dict(terminal=True, primary=is_primary, receipt_sha256=digest(canonical(receipt)))
```

Классификацию primary и разрешение оператор получает из независимой политики
кампании. Для primary он предварительно подтверждает пригодность сохранённых
материалов и доступность ключей для повторного чтения. Функция
`retained_copy(stem) -> bytes` перечитывает соответствующий файл из этой
независимой приватной копии. Адаптер сам сверяет все размеры и SHA-256,
включая control, до первого удаления. При `primary=False` требуется такое же
терминальное разрешение на точную квитанцию.

Очистка сверяет тег, целевой SHA, metadata release по тегу и ID, его встроенный
список и отдельный список assets с `per_page=6`. У каждого присутствующего
файла проверяются точный ID, имя, размер, digest и состояние uploaded.
Каждому удалению по ID предшествует повторное чтение списка. После каждого
DELETE проверяется отсутствие ID. Только после подтверждённого пустого списка
удаляются release и затем точный lightweight tag. Итог проверяется чтением
по ID, тегу и положительными запросами к репозиторию, его списку releases и
default branch. Успешный `cleanup` возвращает `None`.

| Наблюдение | Действие оператора |
| --- | --- |
| Срок чтения истёк или job отменён | Остановить consumers. После terminal state использовать сохранённую квитанцию и независимое разрешение. Возраст release не запускает удаление, срок хранения на GitHub контролирует оператор. |
| До первой загрузки уже есть тег, release или чужой draft | Остановиться и проверить namespace и журнал. Повтор публикации в том же attempt запрещён. |
| Перенос запроса завершился ошибкой после записи, а ID отсутствует в журнале | Сохранить данные для расследования. Не восстанавливать полномочия из имён файлов или нового listing. Сверить независимое подтверждение автора операции, затем принимать отдельное решение владельца. |
| Прерывание после подтверждённого checkpoint или в процессе удаления | Запустить cleanup с последней доверенной квитанцией и свежим терминальным разрешением. Отсутствие уже удалённых объектов проверяется по их исходным ID. Любое расхождение с оставшимся списком останавливает обработку. |
| 403, потеря видимости, неполный listing, неверный hash или чужой asset | Диагностировать с reader в приватном контуре. Сохранить журнал и копию для повторной проверки. Квота и срок ожидания требуют контроля до подтверждённой очистки. |

После успешной проверки оператор отзывает временные credentials и сохраняет
материалы, нужные для разрешённого replay. Для потерянного ответа на создание
тега или release без подтверждённого checkpoint происхождение объекта может
оставаться неопределённым. Автоматическая очистка такого объекта запрещена.

## Проверка компонента

Из корня checkout в Python 3.12 с зависимостями проекта:

```text
python -m unittest scripts.ci_private_assets_qualification
python -m coverage run --branch --source=scripts.ci_private_assets -m unittest scripts.ci_private_assets_qualification
python -m coverage report -m
python scripts/check_docs.py
```

Тесты используют замену удалённого API с состоянием и моделируют отказ между
изменениями. Фактическое выполнение в GitHub, выдача прав и независимый replay
primary требуют отдельной проверки в разрешённой кампании.
[Документация GitHub по releases](https://docs.github.com/en/rest/releases/releases),
[assets](https://docs.github.com/en/rest/releases/assets) и
[Git references](https://docs.github.com/en/rest/git/refs).
