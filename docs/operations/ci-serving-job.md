# Приём исходного кандидата в задании serving

Задание `serving` выполняет M13/M14/M15 на кандидате, замороженном производителем. Вызывающий код получает путь к приватному архиву и параметры его повторного чтения. Запускать на отдельном стандартном GitHub-hosted Ubuntu runner с уже загруженным исходным образом, закреплёнными инструментами и чистым checkout. [Приёмник](../../scripts/ci_serving_job.py), [исходная процедура M13/M14/M15](ci-serving-native.md).

## Вызов из доверенного workflow

```python
from scripts import ci_serving_job

result = ci_serving_job.run(
    root,
    source_api=public_metadata,
    api=read_client,
    trust_key_path=original_trust_path,
    key=transport_key,
    trusted_public=producer_public_key,
    run_owner=producer_owner,
    source=source,
)
```

`source_api` читает только публичные метаданные запуска. `api` открывает файлы релиза через клиент приватного хранилища с правом чтения. Оба клиента подготовить в вызывающем коде. Ключ проверки управляющей записи поступает через доверенный выход задания `producer`, исходный ключ доверия поступает отдельным секретом. `source` содержит ревизию, отпечаток исходников и ID образа. В `run_owner` передать репозиторий, ID запуска, номер попытки и `producer_job="producer"`. До чтения пакетов и создания локальных ресурсов общий `ci_campaign_guard.authorize` проверяет фактический runner, задание `serving`, workflow, ветку, запуск, попытку и точный источник.

## Что проверяет задание

1. `open_consumer` проверяет подпись производителя и связь обеих копий кандидата с одним исходным содержимым. Для `serving` он открывает `candidate-serving` и присоединяет исходные материалы M02/M03/M07 из `upstream-serving`. Штатный читатель сверяет полученный отдельно ключ доверия с замороженным реестром. [Передача между заданиями](../../scripts/ci_campaign_handoff.py).
2. Приёмник создаёт собственный журнал в `.runtime/ci-serving-job`. Идентификаторы производителя, среды потребителя и журнала должны различаться. Штатная процедура импортирует кандидата и `validation-serving` в свою SQL-базу, сверяет контейнер и порт, запускает M13, M14 и M15 по порядку. Перед каждым этапом она повторно проверяет образ, источник и окна всех трёх пакетов. Минимум 600 секунд остатка для исходного предложения и политики сохраняется. [Управление ресурсами](ci-serving-recovery.md).
3. Очистка останавливает SQL потребителя по проверенному ID и проверяет удаление принадлежащих ему кластеров. Контейнер и том SQL сохраняются до удаления одноразового runner. Приёмник дважды проверяет состояние остановленного SQL, до и после сохранения материалов. Наблюдение за SQL производителя выполняет сам производитель. Его подписанные `workspace_id`, `container_id` и `offline_pin` возвращаются в `origin` для итоговой сверки.
4. После закрытия обоих контекстов приёмник проверяет отсутствие временного каталога и перечитывает журнал очистки. Полный `ci_serving_retention.replay` заново читает сохранённые материалы по исходным полномочиям и закреплённому индексу. Перед возвратом результата приёмник снова сверяет источник с образом. [Состав и проверки архива](ci-serving-primary.md).

## Результат и отказ

Возвращаемые `destination`, `index_pin`, `arguments` и `replay` нужны доверенному коду для приватного сохранения и повторного чтения архива. `origin` относится к производителю. `consumer_offline`, `cleanup_owner`, `cleanup` и `gate_counts` относятся к приёмнику. `release_ready` остаётся `False`. До уничтожения runner вызывающий код отвечает за приватное сохранение необходимых свидетельств.

Вызов занимает один процесс целиком. Потоки вывода Python и дочерних процессов, а также файлы команд GitHub направлены в системное пустое устройство. Дочерние процессы получают ограниченный набор системных переменных и метаданных runner. Исходное окружение восстанавливается при возврате и исключении. Содержимое результата и материалы из рабочего каталога запрещено выводить в логи, outputs, summary или публичные артефакты.

При ошибке после начала работы с ресурсами очистка выполняется внутри контекста и повторяется по локальному журналу при выходе. Для восстановления на том же runner вызвать `ci_serving_job.cleanup(root, source_api=public_metadata, run_owner=producer_owner, source=source)`. Успех требует четырёх положительных результатов для M13, M14, M15 и SQL. Код отказывает при чужом или отсутствующем журнале. При пометке `serving_cleanup_unverified` сохранить журнал приватно для разбора. Запуск поверх прежнего каталога, продление окна и удаление по имени ресурса исключены.

[Квалификация](../../scripts/ci_serving_job_qualification.py) использует подписанные тестовые пакеты, контролируемые наблюдения Docker и реальный журнал восстановления. Она проверяет раздельное владение, отрицательные сценарии и порядок повторного чтения. Подтверждение времени и результатов самих M13/M14/M15 требует отдельного hosted-запуска на исходном кандидате.
