# Подготовка четырёх приватных пакетов из одного proposal

Владелец hosted producer вызывает функцию один раз на подготовленном состоянии
с проверенным source-only image, исходным ключом доверия, storage demo и отчётами
M02/M03/M07. Producer SQL должен оставаться доступным до возврата. Вызывающий код
проверяет ожидаемый image, ведёт приватный лог и управляет кластером и SQL.
Обычные роли publisher и promoter участвуют в создании proposal по действующим
правилам. Успех упаковки сам по себе не даёт разрешения на выпуск.

```python
from scripts.ci_campaign_producer import prepare

result = prepare(root, root / ".runtime", key=aes_key)
owner, reports, sealed = result["owner"], result["reports"], result["sealed"]
```

`aes_key` передаётся как 32 байта из приватного канала. `owner` содержит
`freeze_pin`, `freeze`, `expected`, `run_owner`. В `reports` находятся
SHA-256 исходных файлов M02, M03 и M07, включая завершающий перевод строки.

| Имя в sealed | Фаза в context | Содержимое |
| --- | --- | --- |
| candidate-shared | M11-M12 | Исходный замороженный кандидат |
| candidate-serving | M13 | Тот же архив кандидата |
| upstream-serving | upstream-M13 | Исходные отчёты и первичные данные M02/M03/M07 |
| validation-serving | validation-M13 | Байты validation из producer storage по digest подписанного manifest |

Каждый пакет содержит `envelope` с байтами шифротекста, `context`,
`ciphertext_sha256`, `handling="private"` и `release_ready=False`. У обоих
пакетов кандидата также есть `manifest_sha256`. Перед возвратом helper сравнивает
хеш архива и manifest между фазами, повторно проверяет исходный image и source,
а также действительность всех четырёх контекстов. На часах producer до исходного
истечения proposal и policy должно оставаться минимум 600 секунд.

Ключ, файлы, хеши и результат остаются в приватном контуре. После успешного
возврата владелец может остановить свой SQL и отдельно подтвердить offline
observation. Интегратор связывает исходного владельца, pins и наблюдение
подписанной контрольной записью. Consumer проверяет независимые ожидания
и использует обычные адаптеры материализации и приёмки.

## Отказ и восстановление

- Если найдены прежний proposal, freeze receipt или содержимое `release-proposals/`,
  запуск останавливается до создания новой подписи. Проверить существование этих
  путей и принадлежность каталога текущему запуску можно в приватной рабочей области.
- Перед вызовом qualifier helper атомарно создаёт каталог `ci-campaign-proposal-claim`
  в producer state. Он сохраняется после прерывания, поскольку SQL мог уже принять
  предложение. При повторном вызове сохранить исходное состояние для разбора,
  проверить приватные свидетельства producer и передать владельцу решение о новой
  попытке в свежей рабочей области. Снятие claim вручную допускает повторную выдачу.
- При расхождении source, отчёта или validation digest, ошибке чтения SQL или
  исчерпанном окне остановить передачу. Проверить исходные данные и время в приватном
  логе. Обработчик вызывающей стороны отвечает за cleanup своих ресурсов и
  сохранение доказательств. На отказе helper не возвращает частичный комплект.

## Проверка без инфраструктуры

Из корня checkout в подготовленном окружении Python 3.12 запустить

```console
python -B -W error -m unittest scripts.ci_campaign_producer_qualification scripts.ci_consumer_native_qualification scripts.ci_serving_native_qualification
```

Ожидаемый результат - `OK`. Проверяются один вызов qualifier и freeze, одинаковые
байты обоих архивов после расшифровки, исходные отчёты и validation, конкурирующий
вызов, прерывание и потеря окна после последнего seal. Проверки используют
синтетические подписанные данные и штатное шифрование AES-GCM. SQL и hosted source
заменены тестовыми границами. Фактическая межзаданийная передача, offline observation
и общий M18 требуют отдельного запуска.
