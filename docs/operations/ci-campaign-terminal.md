# Терминальная очистка приватного релиза кампании

Оператор может удалить рабочие копии пяти файлов после завершения конкретной попытки публичной кампании. Для этого нужны три независимых источника: метаданные заданий GitHub, подписанный журнал издателя и проверяемая долговременная приватная копия первичных материалов. [Контроллер](../../scripts/ci_campaign_terminal.py) вызывает [штатную очистку хранилища](private-assets.md). Workflow и вызов с реальными полномочиями относятся к следующему этапу.

## Что подготовить

- Из проверенного коммита workflow взять полный состав ожидаемых заданий данной попытки, включая `producer`. Использовать точные имена, которые Actions возвращает в поле `name`. Контроллер поддерживает от 1 до 32 уникальных имён. Задания с результатом `skipped` входят в список. Получать ожидаемый состав из проверяемого ответа API нельзя.
- По независимому каналу оператора получить исходные `run_owner` и `source` согласно [контракту передачи](campaign-handoff.md). Зафиксировать также последнюю полную запись журнала (`expected_tip` с полями `step, asset_id, sha256`). Коммит и отпечаток исходников, ID образа и номер попытки относятся к исходному издателю.
- Закрыть попытку для записи и сериализовать публикацию и очистку её namespace, как требует [регламент хранилища](private-assets.md). Отдельный клиент с полномочиями записи нужен только для рабочего приватного релиза. Для публичной проверки использовать отдельный клиент чтения с фиксированным origin `https://api.github.com`, ограничением размера ответа и тайм-аутом. Для чтения журнала использовать отдельные полномочия чтения.
- Сохранить первичные материалы издателя и потребителей, в том числе свидетельства об отказе или отмене. Источник долговременной копии должен пережить потерю runner и удаление рабочего релиза. Оператор сохраняет исходные доверенные ключи в установленном контуре и проверяет доступность разрешённого архивного replay. Закрытые ключи, приватные ID и хеши не передаются в аргументах команд или публичных outputs.

## Контракт вызова

`cleanup(api, *, source_api, run_owner, source, expected_jobs, expected_tip, read_journal, replay_retained)` возвращает `None` после проверки фактического удаления. Значения `receipt`, `terminal` и классификацию `primary` пользователь передать не может.

| Зависимость | Что должен сделать вызывающий код |
| --- | --- |
| `source_api(method, path)` | Прочитать JSON по фиксированному относительному пути публичного репозитория. Контроллер вызывает только GET. |
| `read_journal(*, run_owner, source, expected_tip)` | Выполнить полную проверку подписей, расшифровки, последовательности записей и внешнего указателя с помощью `ci_campaign_journal.recover`. Клиент приватного журнала, место хранения, ключ расшифровки и доверенный открытый ключ привязываются оператором заранее. Ожидаемый результат содержит `complete=True`, точный `tip` шага 8 и `checkpoint` с полями `storage, issuer`. Частичный журнал предназначен для диагностики. |
| `replay_retained(*, run_owner, source, tip, checkpoint, terminal)` | Заново прочитать независимую приватную копию и проверить исходную запись издателя, исходный кандидат, доступность необходимых ключей и первичные свидетельства для указанных работ и их фактических исходов. При отказе или отмене проверить сохранившиеся материалы соответствующей попытки. Если доказать сохранность и пригодность к replay нельзя, завершиться ошибкой. |
| Результат replay | Вернуть ровно `verified=True`, `binding_sha256` и функцию `read_asset(stem, limit)`. Хеш вычисляется как `digest(canonical(binding))` после успешной проверки, где `binding` содержит пять именованных аргументов replay. В `terminal` входят числовой `workflow_id`, итог попытки `conclusion` и словарь `jobs` с точными ID и итогами заданий. Хеш связывает результат внешнего проверяющего с этим запросом. Доверие к проверяющему и независимость копии обеспечивает оператор. |
| `read_asset(stem, limit)` | Прочитать исходные зашифрованные байты из той же долговременной копии с заданным пределом размера. Штатный адаптер сверяет формат, точную длину и SHA-256 всех пяти файлов до первого DELETE. Ключи и содержимое журнала остаются в своём контуре. |

## Как контроллер принимает решение

1. Проверяет публичный репозиторий `Abrakadabra124/trusted-mlsecops-platform` с ID `1407811916`, владельца, публичную видимость и `fork=false`. Проверяет существование исходного коммита. В сводке запуска и в записи точной попытки сверяет ID запуска, ID workflow, исходные репозитории, SHA, ветку `qualify/candidate-cross-job`, путь `.github/workflows/candidate-cross-job.yml` и событие `workflow_dispatch`. Ожидаемый SHA берётся из проверенного оператором источника. Тип ref исходного задания подтверждался при допуске издателя и привязан через журнал.
2. Получает конкретную попытку по `actions/runs/{run_id}/attempts/{attempt}` и её задания по тому же пути с окончанием `/jobs?per_page=100`. Сверяет `total_count`, длину списка и точный состав ожидаемых имён. Каждый ID задания уникален, каждое задание привязано к этому run, attempt и SHA. У попытки и у всех заданий должны быть `status=completed` и известные терминальные результаты.
3. Если уже началась следующая попытка, решение по прежней принимает из записи прежней попытки и её заданий. Новая попытка имеет собственный namespace. Будущий номер попытки, смена ID workflow, противоречие между сводкой и записью текущей попытки или неполный ответ останавливают операцию.
4. Восстанавливает полную квитанцию из проверенного журнала и сверяет привязки управляющего файла и четырёх пакетов. Затем вызывает приватный replay. Перед выдачей разрешения штатному адаптеру повторно читает публичные метаданные. При смене ID или результата задания, результата попытки либо откате номера последней попытки отказывает. Порядок элементов в списке заданий роли не играет.
5. Штатный адаптер всегда получает `primary=True` для точного хеша квитанции, включая случаи `failure` и `cancelled`. Он проверяет сохранённые байты, принадлежность каждого рабочего объекта и конечное отсутствие по исходным ID. Истечение окна потребления само по себе не даёт полномочий на удаление. Архивная проверка не продлевает исходное окно и не выдаёт разрешения на выпуск.

## Действия при отказе

| Наблюдение | Действие оператора |
| --- | --- |
| Попытка ещё выполняется, ожидаемый список заданий неполон либо GitHub недоступен | Сохранить журнал и рабочие файлы. Для нового решения получить положительное подтверждение по исходному номеру попытки. |
| Подписанный журнал неполон, внешний указатель расходится либо отсутствует подтверждённый ID файла | Остановить очистку и сверить происхождение объекта по приватным свидетельствам. Имя файла или свежий список релиза не дают полномочий на удаление. |
| Сохранённый файл повреждён или архивный replay не подтвердил первичные свидетельства | Оставить рабочую копию, восстановить независимую копию в разрешённом контуре и повторить проверку сохранности. Успех публичных заданий не заменяет replay. |
| Соединение оборвалось после DELETE | Считать исход операции неподтверждённым. Контроллер не повторяет запрос. Перед отдельным решением оператора сверить уже удалённые и оставшиеся ID по подписанной квитанции согласно регламенту хранилища. Сохранить ключи и журнал для восстановления. |

Локальная [квалификация](../../scripts/ci_campaign_terminal_qualification.py) использует публичные ответы и приватное хранилище в памяти. Она проверяет решения контроллера и штатную очистку. Проверка доступа к реальному архиву и запуск терминального workflow остаются отдельными этапами.

Для обоих потребителей есть готовая реализация параметра `replay_retained` в
[ci_terminal_primary.py](../../scripts/ci_terminal_primary.py). Оператор передаёт
независимые публичные ключи с числовыми ID заданий, проверенный приватный релиз
с результатами и отдельный источник сохранённых исходных файлов производителя.
Перед очисткой контроллер сверяет ID успешных заданий с исходной попыткой,
проверяет пять исходных файлов и повторяет штатные проверки обоих потребителей.
[Инструкция по восстановлению](ci-primary-recovery.md).

В `ci_terminal_primary.cleanup_from_archives` приватный клиент чтения проверяет
закрытый журнал по внешней последней записи, открывает отдельный релиз с пятью
исходными файлами и читает результат каждой роли из третьего релиза. Для
удаления рабочего релиза передаётся отдельный клиент издателя. Совпадение ID
любых из трёх архивных релизов или совпадение с рабочим релизом останавливает
операцию до удаления. [Подготовка и публикация кандидата](original-producer.md).
