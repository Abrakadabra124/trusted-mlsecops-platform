# Проверка прав на файлы приватного релиза

Операция `verify-store-permissions` использует отдельный предварительный релиз в `Abrakadabra124/trusted-mlsecops-ci-private`. Он содержит синтетический файл, привязанный к номеру запуска и попытки. Шаги проходят на стандартных публичных GitHub-hosted runner. В приватном репозитории перед подготовкой сверяют активные workflow и исключают запуск по событиям тега и релиза.

## Подготовка оператором

Из рабочего checkout с зафиксированными зависимостями и локальной сессией GitHub CLI создать новый каталог квитанции в личном каталоге вне Git. Передать полный путь. Команду запускает владелец во внешнем доверенном контуре.

```console
python -B -m scripts.ci_probe_fixture create "<absolute-private-directory>"
```

Команда сверяет ID и приватность репозитория, резервирует новый тег и создаёт пустой предварительный релиз. Операторский ключ Ed25519 подписывает его числовой ID, SHA приватного коммита, ID репозитория и одноразовое случайное значение. Закрытый ключ существует только на время подписи. Выход `probe_nonce` и открытый `probe_public` разрешены для ручного запуска. Локальная квитанция и содержимое релиза остаются в приватном контуре.

## Запуск в защищённых средах

1. Для новой версии использовать отдельную ветку `qualify/store-access-v2`. Её исходный коммит указан ниже. Сверить полный SHA, блокировку ветки, применение к администраторам, запреты force-push и удаления. Выполнить на этом SHA ручной `contracts` без доступа к средам. Проверить список workflow, запрашивающих среды, и полный diff относительно ранее проверенной версии.
2. Если владелец разрешил временный перевод сред, сверить отсутствие активных запусков и по одному обновить существующие правила `candidate-store-write` и `candidate-store-read`. В каждой среде должно остаться ровно одно правило типа `branch` с точным именем проверенной заблокированной ветки. Исходные ID правил и прежнее имя сохранить приватно. [API правил веток среды](https://docs.github.com/en/rest/deployments/branch-policies).
3. Для `candidate-cross-job.yml` выбрать `workflow_dispatch`, закреплённую ветку, операцию `verify-store-permissions` и два публичных значения оператора. Каждый job получает только секрет своей среды на последнем шаге. Успешный запуск требует всех четырёх результатов.

| Job | Измеряемый результат |
|---|---|
| `contracts` | Проверки кода прошли на SHA запуска до обращения к приватному секрету. |
| `probe_upload` | Издатель загрузил `publisher.bin`, затем проверил ID, контрольную сумму и прочитал точные байты по ID. |
| `probe_reader` | Читатель скачал те же байты. Попытка загрузки `reader.bin` вернула явный HTTP 403 с сообщением об отсутствии разрешения. Список объектов остался прежним. |
| `probe_cleanup` | Издатель сверил файлы и удалил принадлежащие попытке объекты. Каждый удалённый ID вернул 404, а повторная проверка релиза и списка файлов подтвердила отсутствие файлов. |

4. Дождаться терминального состояния всех заданий и снять независимое показание через API GitHub Actions. Восстановить прежнее точное правило `qualify/candidate-cross-job` в каждой среде и заново прочитать оба списка. В приватном каталоге сохранить ID запуска, SHA, исход операции и результат восстановления правил.
5. Владелец закрывает свой пустой релиз по исходной квитанции и проверяет отсутствие релиза и тега.

```console
python -B -m scripts.ci_probe_fixture retire "<absolute-private-directory>"
```

## Действия при отказе

| Наблюдение | Действие |
|---|---|
| Читателю удалось записать файл | Считать разделение прав нарушенным. Дождаться задания очистки. Заменить токен читателя на fine-grained токен с `Contents: Read-only` единственного приватного репозитория. |
| Ответ 403 связан с квотой, SSO или временным ограничением | Сохранить результат как неподтверждённый. После устранения причины создать новый тестовый релиз и выполнить новую попытку. |
| Прервалась загрузка, список содержит чужой объект или изменилась подпись | Закрыть временный допуск к защищённым средам после остановки заданий. Сверить локальную квитанцию, ID, точные имена и байты через приватную сессию. Автоматическая очистка останавливается при расхождении. |
| Оператор потерял подтверждение при подписи описания релиза | Повторить чтение через `python -B -m scripts.ci_probe_fixture confirm "<absolute-private-directory>"`. Команда сверяет подпись, ID, исходный тег и пустой список файлов и сохраняет исходную квитанцию. |
| Оператор потерял ответ при удалении своего пустого релиза | Повторить `retire` с тем же каталогом квитанции. Команда сверяет состояние по ID, тегу и списку релизов и может закончить уже начатую очистку. |

Результат распространяется на эти два токена, этот репозиторий и операции с файлами релиза во время измерения. Для приёмки M11 требуются исходный кандидат, прохождение его штатных проверок и сохранённые первичные свидетельства.

### Что проверить при неоднозначном отказе

В обновлённом коде после попытки записи читатель снова запрашивает список
файлов, в том числе при ошибке чтения ответа. Метка `inventory_unchanged`
означает, что встроенный список и отдельный запрос совпали с исходным составом
и ID. При неизвестной причине HTTP 403 этот результат сам по себе сохраняет
отказ в допуске. Если последней меткой просмотра ответа была `denial_body`,
остановилось ограниченное чтение байтов. Для остальных проверок используются
`denial_json`, `denial_fields`, `denial_status`, `denial_message` и
`denial_documentation`. В журнал попадают только названия этапов, без полей
и значений удалённого ответа. Эти метки относятся к обновлённому коду, запуск
44818377962 выполнялся на предыдущей версии.

Для версии `d8c8878fec5b6124b178a45eb8afbb6be2a25b2c` на защищённой
ветке `qualify/store-access-v3` один запрос записи также различает пустое
тело ответа (`denial_empty`), объект с единственным общим сообщением
`Forbidden` (`denial_generic`) и объект с единственным сообщением
`API rate limit exceeded` (`denial_rate_message`). Во всех трёх случаях
допуск остаётся закрыт. Завершающая сверка проверяет точные ID и состав
файлов независимо от разбора ответа. При повторении общего или неизвестного
403 оператор сохраняет результат и проверяет конфигурацию доступа у владельца
GitHub. Автоматические повторы для угадывания формата ответа отсутствуют.
Результат прогона только с операцией `contracts` удостоверяет код проверки.
Для допуска кампании нужны отдельная успешная попытка с этим точным SHA,
назначенный оператором указатель и положительный итог всех четырёх заданий.
