# Локальная очередь ручного рассмотрения T19

Когда оператор не нашёл разрешённый совместимый bundle, клиент может поставить
конкретную заявку в локальную очередь. Для этого нужен порт **собственного**
lab serving на 127.0.0.1, приватный файл действующего prediction-токена и
выданный вызывающей стороной непрозрачный SHA-256 заявки (64 строчных hex-символа).
Связь digest с заявкой хранит вызывающая сторона. Используйте отдельный digest
для каждой заявки. Токен, содержимое запроса и HTTP request ID для этого не подходят.
Используйте существующий каталог состояния сессии. Он должен принадлежать оператору и быть закрыт для других
пользователей. На Windows доступ к нему и файлу токена ограничивает владелец через ACL.

## Поставить заявку и проверить очередь

Пример для shell из корня checkout с установленными зависимостями. Передайте
переменными `CASE_SHA256` и `PORT` идентификатор заявки и порт, а в
`PREDICTION_TOKEN_FILE` укажите путь к файлу токена. JSON поступает через stdin.
В примере все шесть признаков синтетические.

```sh
printf '%s' '{"schema_version":1,"instances":[{"change_size":0.4,"failed_checks":0.1,"dependency_changes":0.2,"test_coverage":0.8,"change_entropy":0.3,"prior_failure_rate":0.1}]}' |
  python -m mlsecops.manual_review --state .runtime submit \
    --case-sha256 "$CASE_SHA256" --port "$PORT" --token-file "$PREDICTION_TOKEN_FILE"

python -m mlsecops.manual_review --state .runtime list
```

`submit` отправляет один обычный авторизованный `POST /v1/predict`.
Только HTTP 503 с точным `error.code=model_unavailable` и корректным
ответом serving создаёт запись. Код сообщает о недоступности оценки.
Причину отказа оператор устанавливает отдельно. При HTTP 200, 401, 429,
другом коде ошибки, некорректном ответе или обрыве связи команда завершается
с кодом 1. Проверьте порт, право на prediction и состояние serving.

`list` работает при остановленном serving, выводит JSON-массив и не требует
токена. Найдите в нём свой `case_sha256` со статусом `pending human review`.
Пустой массив означает пустую очередь. Каждый элемент представлен пустым
файлом `.runtime/manual-review/<case_sha256>`. Повторная подача с тем же digest
идемпотентна. Если запись повреждена, команды отклоняют её. Сохраните каталог
для разбора. Доступ к исходной заявке оператор получает в системе caller по digest.

На Linux перед подтверждением клиент вызывает `fsync` для файла, каталога
`manual-review` и родительского каталога состояния. Если синхронизация
завершилась ошибкой, файл уже может быть виден в `list`. Устраните ошибку
хранилища и повторите `submit` с тем же digest до кода 0. Повтор проверяет и
синхронизирует существующий пустой файл. Для очереди требуются приватные
права каталога и файлов. На Windows клиент синхронизирует файл, а дескриптор
каталога для `fsync` в этом режиме недоступен.

Код 0 у `submit` подтверждает наличие записи только в этой локальной очереди.
Рассмотрение человеком, внешняя доставка и разрешение на выпуск требуют
отдельных действий. Обязательные release gates продолжают действовать.
См. [контракт serving](../serving-api.md) и [порядок отката](bundle-rollback.md).
