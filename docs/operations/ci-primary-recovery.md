# Восстановление первичных свидетельств M11-M15 после остановки runner

У `shared` (M11/M12) и `serving` (M13/M14/M15) разные результаты и разные одноразовые ключи подписи. У обоих заданий должен быть один исходный кандидат, выпущенный одним `producer` в одной попытке GitHub Actions. Все свидетельства и их контрольные суммы хранятся в приватном контуре.

## Сохранение

1. Штатный потребитель скачивает подписанный пакет производителя, выполняет свои проверки и освобождает собственные ресурсы. После закрытия рабочей области он открывает сохранённые файлы заново. Результат включает исходные параметры, индекс файлов, наблюдения об остановке и итог повторной проверки.
2. Контроллер берёт байты индекса и перечисленных в нём объектов. Каждый объект проверяется по размеру и SHA-256. Порядок задан индексом и сортировкой SHA-256. Посторонние файлы runner, исходные ключи и журналы процессов в пакет не входят.
3. Контроллер подписывает сведения об исходном запуске, роли, наблюдениях, индексе и содержимом пакета одноразовым ключом Ed25519. Затем шифрует подписанный заголовок и объекты через AES-256-GCM с отдельным ключом, производным от ключа канала. Шифротекст вместе с заголовками должен помещаться в лимит транспорта. При превышении проверка завершается отказом до загрузки.
4. Издатель загружает зашифрованный файл в заранее закреплённый приватный предварительный релиз этой попытки. В нём предусмотрены `shared.bin` и `serving.bin`. После загрузки издатель проверяет ID, размер, digest и заново читает все байты. Повтор с теми же байтами допустим. Если по тому же имени лежат другие байты, издатель останавливается.
5. Открытый ключ проверки принимают из доверенного выхода соответствующего задания. Идентификаторы приватных объектов, их контрольные суммы, исходные пакеты, ключи шифрования и квитанции сохраняют в приватном контуре.

## Команды контроллера на hosted runner

После получения проверенного образа источника задание `shared` или `serving` выполняет две команды в отдельных процессах. Первая читает исходный кандидат, вторая получает права на запись только для публикации подготовленного результата.

```console
.venv/bin/python -B -W error -m scripts.ci_primary_job capture
.venv/bin/python -B -W error -m scripts.ci_primary_job publish
```

| Вход процесса | Откуда его получает контроллер |
|---|---|
| `CANDIDATE_PUBLIC_TOKEN` | Токен текущего задания для чтения исходного репозитория и метаданных Actions (`contents: read` и `actions: read`). |
| `CANDIDATE_TRANSFER_KEY` | Ключ канала, 32 байта в Base64, из приватного контура. |
| `capture` | Только `CANDIDATE_STORE_READ`, открытый ключ производителя в `CANDIDATE_PRODUCER_PUBLIC` и абсолютный путь `CANDIDATE_TRUST_FILE` к исходному защищённому ключу вне checkout. |
| `publish` | Только `CANDIDATE_STORE_WRITE`, открытый ключ из успешного шага capture в `CANDIDATE_RECEIVER_PUBLIC` и закреплённый оператором JSON-объект `CANDIDATE_PRIMARY_RELEASE`. |

Под «только» в последних двух строках понимается выбор учётных данных **приватного хранилища**. JSON-объект релиза содержит `repository_id`, `release_id`, `name`, `target_commitish`. Идентификаторы, ключи и пути передаются в окружении соответствующего процесса. Оба процесса используют одну доверенную локальную рабочую область. Внешний оператор может повторить проверку в checkout той же ревизии через `ci_primary_job.replay_remote`.

У текущих двух защищённых сред GitHub разные секреты. Задание Actions выбирает одну среду на весь job. Для включения этих двух шагов на одном runner интегратор должен заранее обеспечить раздельную подачу прав на уровне шагов. Проверенная операция `check-private-access` запускает два отдельных задания и подтверждает чтение каждой ролью.

## Восстановление

Зафиксировать исходную попытку, версию исходников, образ и внешний идентификатор приватного релиза. Из подписанного контрольного документа производителя получить исходную фиксацию кандидата и идентичность создавшей его рабочей области. Для каждой роли прочитать её зашифрованный файл и взять ключ проверки из доверенного выхода этой роли.

Контроллер расшифровывает файл, сверяет подпись, роль, исходную попытку и кандидата. Затем восстанавливает объекты в новом временном каталоге под `.runtime` и вызывает обычный `m18_shared_retention.replay` либо `ci_serving_retention.replay`. Он сравнивает результат с подписанной контрольной суммой первоначальной проверки. Проверяющему нужны точные исходники и зависимости. В чистом checkout контроллер сам создаёт каталог .runtime и удаляет временные файлы проверки после чтения. Для исторического чтения поднимать SQL или Kubernetes заново не требуется.

| Что произошло | Действие оператора |
|---|---|
| Связь оборвалась после загрузки | Сохранить исходный шифротекст. Повторно проверить закреплённый приватный релиз. Повтор загрузки допустим для тех же байтов. Повторная упаковка создаёт другой шифротекст и другую подпись. |
| Подпись, роль или исходный кандидат расходятся | Сохранить релиз и журнал. Сверить попытку, источник открытого ключа и подтверждённый контрольный документ производителя. |
| Файл неполный, изменился SHA-256 или штатный replay вернул другой результат | Сохранить обе копии и исходную попытку. До разбора оставить рабочие объекты на месте. |
| Истёк срок предложения | Использовать историческое чтение. Срок предложения и факт допуска в момент исполнения берутся из исходных свидетельств. |

### Команда для оператора восстановления

Для каждой роли оператор сохраняет отдельную квитанцию JSON с полями `role`, `release`, `run_owner`, `source`, `trusted_public`, `owner` и `origin`. Значение `trusted_public` берут из исходного задания этой роли. `owner` и `origin` берут из проверенного управляющего документа издателя. Приватный релиз и исходный SHA сверяют с ранее записанными оператором значениями. Квитанция нужна независимо от восстанавливаемого файла.

1. Открыть чистый checkout исходной ревизии, содержащей команду `replay`. Хранить квитанцию за пределами checkout в обычном файле до 64 КиБ. На POSIX файл должен принадлежать оператору и иметь права `0600`.
2. Через доверенное локальное хранилище передать процессу `CANDIDATE_STORE_READ` и `CANDIDATE_TRANSFER_KEY`. Для запуска `shared` указать абсолютный путь к его квитанции в `CANDIDATE_REPLAY_RECEIPT`. Для `serving` сменить путь на квитанцию второй роли.
3. Из корня checkout выполнить команду для выбранной роли.

```console
uv run --locked python -B -W error -m scripts.ci_primary_job replay shared
uv run --locked python -B -W error -m scripts.ci_primary_job replay serving
```

Команда сверяет SHA и чистоту checkout, скачивает исходный зашифрованный пакет через клиент только для чтения, проверяет подпись, распаковывает свидетельства во временный каталог и повторяет штатную проверку этой роли. Результат виден как `primary_replay=pass` либо `primary_job=refused` с ненулевым кодом выхода. Успех означает, что восстановлены свидетельства выбранной роли. Для удаления рабочей копии нужны также терминальное состояние заданий, внешний указатель на журнал и проверенные независимые копии всех исходных объектов. [Порядок терминальной очистки](ci-campaign-terminal.md).

## Воспроизведение без инфраструктуры

Из чистого checkout с Python 3.12.15 и зафиксированными зависимостями выполнить команду установки и запустить проверки.

```console
uv sync --locked --no-build --python 3.12.15
uv run --locked python -B -W error -m unittest scripts.ci_primary_carrier_qualification scripts.ci_primary_store_qualification scripts.ci_primary_handoff_qualification scripts.ci_primary_job_qualification scripts.ci_terminal_primary_qualification
```

Тесты используют подписанные тестовые данные, файловую систему и штатные функции replay. Внешнее хранилище и наблюдения инфраструктуры в этих тестах контролируются. Для выпуска R1 нужны результаты реальной сквозной кампании и чистое воспроизведение на одном кандидате.

На полном коммите `82684f1a4181ef1c362a8bbc792bbdd19756a13c` в чистом
checkout на Ubuntu 24.04 прошли 462 теста без пропусков за 38,983 секунды.
Для шести новых модулей покрыты все измеренные исполняемые строки и ветви.
В этом запуске использовалось контролируемое приватное хранилище.
