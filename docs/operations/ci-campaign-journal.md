# Приватный журнал публикации T21

[Модуль журнала](../../scripts/ci_campaign_journal.py) сохраняет квитанции
[producer](../../scripts/ci_campaign_handoff.py) в отдельном release
`Abrakadabra124/trusted-mlsecops-ci-private`, ID репозитория `1465012664`.
За подготовку release и исходных параметров отвечает оператор. Для публичного
workflow все квитанции, зашифрованные записи, ID файлов и хэши остаются
приватными. Модуль возвращает данные в памяти процесса.

## Подготовка до dispatch

1. Подготовить пустой опубликованный prerelease в приватном репозитории.
   Закрепить его числовой ID, уникальное имя и точный 40-символьный SHA из
   `target_commitish` в защищённой конфигурации. Имя и тег должны совпадать,
   начинаться с `ci-journal-` и содержать далее до 64 букв ASCII, цифр,
   дефисов или подчёркиваний, с буквой или цифрой в начале суффикса.
   Записи добавляются в обычный изменяемый release. Оператор проверяет
   исходный Git ref при подготовке. При каждом обращении адаптер сверяет
   `target_commitish` в metadata и адресует release по числовому ID.
2. Выделить этот release для одной попытки. Хранилище допускает одного
   publisher. Удаление рабочего release должно оставлять журнал и retained
   материалы доступными. Обзор видимых releases ограничен одной полной
   выборкой до 99 записей. Совпадение имени или тега с другим видимым release,
   заполненная страница или ответ с пагинацией останавливают работу. Существуют
   черновики, доступные только writer, поэтому первоначальную проверку
   выполняет оператор или publisher с соответствующими правами.
3. Оператор заранее закрепляет открытый ключ подписи журнала: стандартный
   base64 для 32 байт Ed25519. Существующий закрытый ключ в защищённом
   файле получает только producer. Он отделён от ключа подписи control и от
   полномочий consumer с правом записи в репозиторий. Для чтения записей нужен
   32-байтовый симметричный ключ; ключ AES-256-GCM выводится через HKDF-SHA256
   с отдельным доменом `MLSJOURNAL\x01`. Оператор сохраняет доступ
   к проверочному и симметричному ключам на весь срок восстановления.
4. Получить `run_owner` и `source` по
   [контракту публичного запуска](../../scripts/ci_campaign_control.py).
   Они содержат исходный repository, run ID, attempt, job, source revision,
   source fingerprint и image ID. Доверенные значения для recovery поступают
   от контроллера и оператора. Адаптер проверяет схемы и криптографическую
   привязку. Проверка реального состояния публичного run принадлежит
   terminal job.

## Публикация

```python
from scripts import ci_campaign_journal

write = ci_campaign_journal.publisher(
    writer_api,
    journal=operator_release,
    run_owner=run_owner,
    source=source,
    key=key,
    trusted_public=operator_public,
    key_path=producer_key_path,
)


def checkpoint(local_checkpoint):
    tip = write(local_checkpoint)
    save_private_witness(tip)
```

`operator_release` содержит ровно `repository_id, release_id, name,
target_commitish`. Передать `checkpoint` в `handoff.publish` или
`publish_original`. `save_private_witness` в примере принадлежит интеграции.
Она синхронно сохраняет последний подтверждённый `{step, asset_id, sha256}`
в независимом защищённом приватном месте, доступном terminal job. Сам
`handoff.publish` игнорирует возвращаемое значение callback. Свидетельство,
заново вычисленное из проверяемого listing, не подтверждает свежесть хвоста.

| Шаг | Поля рабочей квитанции в журнале |
| --- | --- |
| 1 | Зарезервирован тег, ID рабочего release ещё отсутствует |
| 2 | Подтверждён ID рабочего release, файлов пока нет |
| 3, 4 | По очереди добавлены `candidate-shared`, `candidate-serving` |
| 5, 6 | По очереди добавлены `upstream-serving`, `validation-serving` |
| 7 | Те же четыре строки и ключ проверки control с хэшами control и четырёхстрочной квитанции |
| 8 | Подтверждена строка `producer-control`, её SHA-256 совпал с шагом 7 |

На каждом шаге producer подписывает закрытую запись с полным локальным
`{storage, issuer}`, параметрами кампании, номером шага и предыдущим
свидетельством. Ранее подтверждённые поля и ID должны совпасть. Затем он
шифрует подписанную запись с новым 12-байтовым nonce. Максимум восемь
файлов по 16 КиБ, суммарно 128 КиБ. Непосредственно перед upload проверяются
ID, владелец и приватность репозитория. Callback завершается успешно только
после сопоставления upload с listing release и GET по ID файла, чтения
байтов с проверкой размера и SHA-256, расшифрования, проверки подписи и
повторной проверки состава release. Секретов в имени файла нет.

## Восстановление и сохранение primary

```python
audit = ci_campaign_journal.recover(
    reader_api,
    journal=operator_release,
    run_owner=run_owner,
    source=source,
    key=key,
    trusted_public=operator_public,
    expected_tip=independent_tip,
)
checkpoint = audit["checkpoint"]
```

По умолчанию требуются все восемь записей. Результат содержит `checkpoint`,
`tip` и `complete`. Reader проверяет привязку к назначенному release, состав
по именам и уникальным ID, каждую подпись, шифротекст, ссылки между шагами
и конечное свидетельство, если оно передано. Порядок элементов в JSON-списке
GitHub не влияет на порядок проверки. Для исторического аудита допускается
истёкшая квитанция. Проверка подписанного сохранённого control доступна через
[verify_retained_control](../../scripts/ci_campaign_control.py).

| Ситуация | Результат и действие |
| --- | --- |
| Оборван ответ после upload записи журнала | Writer останавливается. Отдельный reader может подтвердить принятый подписанный префикс. Повторный upload и продолжение замороженной попытки запрещены. |
| Принят рабочий файл, но соответствующая запись журнала отсутствует | Сохранить рабочий release целиком. Происхождение лишнего ID нельзя восстановить по совпадению имени и хэша. |
| Пропала последняя запись | Полный reader отказывает. При `allow_partial=True` внешний актуальный `expected_tip` также обнаруживает усечение. Без такого свидетельства подлинный короткий префикс неотличим от более длинного журнала с удалённым хвостом. |
| Утерян или повреждён единственный экземпляр журнала | Для расследования сохранить рабочие объекты и независимые свидетельства. Contents write даёт возможность удалить записи. Подпись обнаруживает подмену, но не восстанавливает утраченные байты. |

`allow_partial=True` служит диагностике. Пустой release даёт `checkpoint=None`,
`tip=None`, `complete=False`. Любая неполная цепочка, неподтверждённый хвост
или расхождение с текущим рабочим inventory исключает автоматическое удаление.
Даже полный журнал удостоверяет только историю producer. Квитанция не является
копией primary. До удаления исходного release отдельный terminal job должен
проверить завершение нужной попытки, независимое разрешение, актуальное
внешнее свидетельство, независимую retained-копию и пригодность ключей для
replay. Когда исходные данные существуют в единственном экземпляре, их
сохраняют. [Условия очистки](private-assets.md).

Локальная проверка использует реальные подписи и шифрование с синтетическими
ключами и заменяет сетевой транспорт:

```text
python -m unittest scripts.ci_campaign_journal_qualification
python -m coverage run --branch --source=scripts.ci_campaign_journal -m unittest scripts.ci_campaign_journal_qualification
python -m coverage report -m
python scripts/check_docs.py
```
