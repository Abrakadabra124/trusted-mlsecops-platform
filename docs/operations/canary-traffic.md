# Поэтапный перевод тестового трафика

Оператор T19 сравнивает две уже проверенные версии на одном синтетическом
запросе. Стабильной версии и кандидату нужны разные идентификаторы bundle
и отдельные локальные HTTP-порты. Для каждой версии вызывающая сторона задаёт
доверенные идентификаторы модели и bundle, а также независимо полученный
ожидаемый score. Порт, токен и эталон для каждой версии передаются вместе.

## Воспроизведение проверки

Из чистого checkout с Python 3.12.15 выполните команды из корня репозитория.

```sh
uv sync --locked --no-build --python 3.12.15
uv run --locked python -B -W error -m unittest scripts.canary_probe_qualification scripts.canary_evaluation_qualification scripts.canary_campaign_qualification
```

Интеграционный тест открывает два временных порта на loopback и отправляет
обычные запросы `POST /v1/predict` с авторизацией. Работают HTTP-обработчик
платформы и два журнала аудита. Тест управляет ответами вычислительных
движков. При 100 запросах на ступень кандидат получает 0, 10, 50 и 100
запросов соответственно. После закрытия обоих серверов тест заново проверяет
записанные наблюдения. Он также изменяет один байт файла и проверяет отказ
при несовпадении SHA-256.

## Как принимается решение

Функция [run](../../mlsecops/canary_campaign.py) измеряет базовую ступень,
затем вызывает отправку и проверку для каждой следующей доли. По умолчанию
она отправляет 200 запросов на ступень. На каждой ступени требуется не менее
100 корректных ответов. Ошибки учитываются в числе всех попыток. Рост доли
ошибок относительно базовой ступени ограничен одним процентным пунктом.
Пределы p95 и p99 составляют 200 и 500 мс для всех попыток и отдельно для
успешных ответов. Идентичность модели, bundle и score проверяется по эталону.

При нарушении критериев функция возвращает `hold` и прекращает увеличение
доли трафика. Для рабочего сценария вызывающая сторона передаёт управление
процедуре отката. При испорченном пакете, подмене ответа или нарушении
порядка измерений проверка отклоняет доказательства. Оператор фиксирует
номер кампании, исходный commit, хеш пакета и последнюю проверенную долю.
Если сервер отдаёт 503, следует проверить готовность и исправность аудита.
При несовпадении model или bundle нужно сверить целевой порт и привязку
к одобренной версии. При превышении задержек нужно сравнить исходную и
последнюю ступени, включая неуспешные запросы.

Первичные строки сохраняются в отдельном каталоге
`.runtime/evidence/canary-<campaign>/traffic.json` при передаче `.runtime`
как каталога состояния. В них входят порядковый номер, выбранная версия,
монотонные времена, код HTTP и ограниченный набор полей ответа.
Для повторной проверки нужны исходные эталоны и закреплённый владельцем
`primary_sha256`. Решение `complete` относится к последовательности трафика.
Для M16 дополнительно требуется измерить откат всего bundle на стенде,
проверить отказ отозванной версии и ручное рассмотрение.

При отказе обоих разрешённых путей оператор открывает заявку через
[локальную очередь ручного рассмотрения](manual-review.md). Процедура
проверяет обычный HTTP-ответ serving и сохраняет идентификатор заявки.
Дальнейшие действия приведены в [ранбуке отката](bundle-rollback.md)
и [регламенте клиента](serving-client-troubleshooting.md).
