# T07. Один кандидат в M03/M04/M05/M07/M20

Оператор запускает [квалификацию](../../.github/workflows/controller-delivery.yml) на одноразовом стандартном Linux runner публичного репозитория. Входы: чистый checkout, locked CPU image, приватный кластер с Cilium, пустые owned SQL обоих профилей. Команды и порядок установки закреплены в workflow.

1. Передать M07 workspace ID пустого host SQL и задать `R1_SCOPED_TRAINING=1` только для joint M07. M03 публикует проверенный dataset. Signed backup и migration связывают исходные таблицы, ключи и UID постоянного тома.
2. Внутри M03 выполнить M04 с его штатным M20. Единственный publisher создаёт training Job в ml-train. Scorer передаёт модель ONNX и features worker в ml-eval и подписывает оценку. Контрольные и отрицательные M20 batches используют тот же candidate и отдельные reservations. Бюджетная кампания M07 работает в отдельной БД.
3. После M04 закрыть private SQL для клиентов. Перенести таблицы candidates и evaluations целиком одним pg_restore в транзакции. Оператор подписывает receipt переноса с digest архива, исходным и конечным ledger. Результат проверяется по обеим БД, включая timestamps и reservations. Предмет и подпись оценки проверяются SQL reader с ожидаемым evaluator key. Host SQL становится единственным доступным хранилищем этой истории. Здесь доверены runner, администратор кластера и локальный signer оператора.
4. Создать proposal после M07. Передать SHA-256 его файла в `R1_ISOLATION_PROPOSAL_SHA256` для M05. Проверить реальный HTTP inference до, во время и после DeadlineExceeded/OOMKilled, затем проверить report bindings командой `python -m scripts.controller_delivery` с пинами demo, proposal и trusted keys. Serving M05 использует bounded Docker ONNX worker на hosted runner. Приёмка M12 и разрешение на выпуск выполняются отдельно.

При отказе посмотреть последний завершённый шаг и очищенную секцию диагностики. Для M07 читать вложенные результаты M03, M04, M20 и компоненты M20. Если отсутствует текущий report, считать проверку незавершённой. При расхождении receipt, ledger, кандидата, подписи или UID прекратить использование обеих копий. При timeout/частичном импорте не открывать private SQL и не переносить строки вручную. Повторить workflow на новом runner с новым workspace. Cleanup проверяет остановку owned host SQL и удаление owned кластера. Raw logs, ключи, dump, kubeconfig и worker payload остаются на runner. Эскалация владельцу нужна при воспроизводимом отказе на чистом runner с тем же SHA.

После передачи среды этот workflow выполняет M08/M09, canary, rollback и восстановление M16/M17. Итоговая команда `python -m scripts.controller_delivery --include-recovery base7` проверяет подпись receipt, идентичность пересекающихся M03/M07 reports и использует действующий recovery reconciler. Пины передаются через `M17_KEYS_SHA256`, `M17_DEMO_SHA256`, `M17_PROPOSAL_SHA256`; revision приходит из `GITHUB_SHA`.

## Передача среды serving после M05

Владелец общего workflow добавляет controller bootstrap после private storage bootstrap и задаёт `R1_SCOPED_TRAINING=1` вместе с `M07_FRESH_WORKSPACE_ID` только на шаге M07. Вложенный M03/M04/M20 создаёт первичный candidate. Затем существующий шаг source фиксирует proposal/demo и ключи. Для M05 передать `R1_ISOLATION_PROPOSAL_SHA256=steps.source.outputs.proposal`.

После M05 и перед созданием ресурсов serving запустить `python -m scripts.controller_serving_handoff`. Передать `M17_DEMO_SHA256=steps.source.outputs.demo`, `M17_PROPOSAL_SHA256=steps.source.outputs.proposal`, `M17_KEYS_SHA256=steps.source.outputs.keys`. Здесь keys означает digest canonical JSON. Отдельный raw keys_file у M10 сохраняет собственную семантику.

Handoff сверяет пять gate reports, signed transfer, копию всей истории в host SQL, pinned demo/proposal, signer identities и отказ настоящему serving-клиенту на старом SQL. Только на штатном GitHub-hosted runner проверяются namespace UID, volume UID, точный kind node и владение его Docker-томами. Удаляется старый кластер. Connection limit старой БД остаётся 0 до удаления. Локальные cluster receipts и credentials перемещаются под .runtime/retired-training-cluster на одноразовом runner. Создаются новый owned-кластер и новый пустой private SQL с новыми UID. Проверяются mTLS, фактическая роль serving и разрешённые/запрещённые SQL-операции с rollback. Полный ledger host SQL, его container ID и заново прочитанный signed proposal должны совпасть до и после. M12 получает обычные пути cluster.json, kubeconfig и kubernetes-storage. Его штатный stage загружает frozen proposal из host SQL. Результат handoff записывается в evidence/controller-serving-handoff.json.

При отказе остановить joint workflow и выполнить штатный owned cleanup. Повторить на новом hosted runner. Никакой этап восстановления этого пути не открывает старую БД. Незавершённый replacement не допускает serving. Успех handoff не закрывает M12, M10 или M11.

В конце базовой ветки выбрать `--include-recovery base7` для M02/M03/M07/M08/M09/M16/M17. На родителе 04bfbca выбрать `--include-recovery parent11`: этот профиль дополнительно требует M01/M06/M10/M12. В обоих случаях действующий delivery reconciler выполняется полностью; затем проверяются точный набор, совпадение M03/M07 и пять scoped reports. Каждый отсутствующий либо неожиданный gate останавливает сборку. Результат содержит отдельные recovery_reports, scoped_reports, их объединение и release_ready=false.

### Совместный профиль M11/M12 и полный M21

На ветке интеграции от 4b02888 push запускает совместный профиль M11-M12.
