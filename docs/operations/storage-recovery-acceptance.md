# M17. Проверка восстановления на одноразовом стенде

Задача оператора - восстановить именно тот снимок, который создала служба по таймеру, и проверить первый корректный ответ сервиса после потери исходного PostgreSQL. Каждый запуск [workflow T20](../../.github/workflows/storage-recovery.yml) начинает с чистого checkout и заканчивает проверкой состояния обоих контейнеров. Локальный Docker для воспроизведения оператору не нужен.

## Воспроизведение

1. Откройте GitHub Actions для ветки `codex/cp4-m23-security-events-20261107`. Изменение перечисленных в workflow файлов запускает **T20 scheduled backup and independent recovery**. Для проверки уже опубликованного коммита используйте **Re-run all jobs** в его запуске. Сверьте полный SHA и номер попытки. Материалы из разных попыток несовместимы.
2. Дождитесь завершения этапа подготовки. Он тренирует CPU-кандидата, оценивает его, сохраняет исходное предложение выпуска и закрепляет SHA-256 трёх входов - отчёта предложения, записи обучения и оценки, доверенных публичных ключей. Владелец стенда сохраняет журнал двух контролируемых подписанных разрешений в том же хранилище.
3. На этапе восстановления systemd временно активирует отдельный экземпляр штатного таймера. Служба записывает согласованную копию данных, артефактов и журнала решений. Идентификатор проверенной копии сохраняется вне исходного хранилища. Проверяющий останавливает исходный PostgreSQL и читает снимок с этим идентификатором в новом экземпляре PostgreSQL с отдельными томом, сетью и клиентскими сертификатами.
4. Проверяющий сравнивает 1 000 прогнозов оценённого кандидата и заново проверяет подписи и предложение выпуска. Исходное предложение требует полного комплекта доказательств. Для HTTP-проверки оператор использует отдельное контролируемое разрешение на те же байты ONNX. Приёмка сверяет хеш модели в обоих случаях. Из восстановленного хранилища ожидаются HTTP 200 и совпадение прогноза с результатом обучения. После отзыва ключа проверяющий заново запускает обработчик. Оба маршрута, `/readyz` и `/v1/predict`, должны вернуть 503. Ещё два случая проверяют отказ до создания нового хранилища при повреждении архива и утрате исходной записи модели в архиве.
5. После cleanup обычная команда приёмки повторно проверяет подписи, исходные хеши, отдельный инвентарь, запись восстановления, владельца ресурсов, временные отметки и остановку обоих экземпляров. Результат ищите в последнем шаге workflow по `M17: pass`, `report_sha256` и метрикам. Самостоятельный запуск CLI без материалов и четырёх значений SHA из этой же попытки даёт `inconclusive`.

```sh
uv run --locked python -B -W error -m mlsecops.acceptance --gate M17 --output .runtime/evidence/M17.json
```

**Как читать время.** RTO - время от начала процедуры до проверки успешного прогноза по HTTP из восстановленного хранилища. Предел для стенда составляет 900 секунд. RPO - возраст восстановленной точки данных к моменту подтверждённой остановки исходной базы. Начало берётся из подписанной отметки SQL-снимка, предел составляет 24 часа. Срабатывание таймера в CI ускорено однократным триггером. Поле `next_elapse_utc` подтверждает установленное следующее расписание. Для вывода о соблюдении расписания несколько суток подряд нужны отдельные наблюдения. Оба хранилища размещаются на одной одноразовой машине.

## Плейбук при отказе

| Где остановилась проверка | Что проверить | Как продолжить |
| --- | --- | --- |
| Таймер или служба | Имя временного unit этой попытки, фактический выход службы, время UTC, отдельный инвентарь и подписанный момент снимка. | Сохранить номер запуска и место ошибки. Устранить причину по [ранбуку расписания](daily-storage-backup.md), воспроизвести всю проверку. |
| Архив отклонён или в нём отсутствует объект | Зафиксированный владельцем backup ID, размер, хеш, ключ подписи и рабочую область из manifest. В отрицательных сценариях ожидается отказ до создания target. | Для восстановления пригодна копия, прошедшая полную проверку по внешнему pin. При неясном исходе импорта действовать по [плейбуку журнала решений](promotion-recovery-troubleshooting.md). |
| SQL восстановлен, сервис не готов | Сверить идентификаторы source и target, клиентский сертификат роли serving, проверку модели и её golden predictions, номер решения и актуальное состояние службы доверия. | Разобрать первый отказ по [ранбуку восстановления кандидата](m17-restore-companion.md). Отозванный ключ требует новой действующей авторизации. Повторная загрузка старой копии сохраняет действие отзыва. |
| Превышен RTO или RPO | Сопоставить момент снимка SQL с остановкой source, затем длительность восстановления с моментом проверенного HTTP-ответа. | Выяснить, устарела сама копия или слишком долго восстанавливался сервис. Зафиксировать провал попытки и измерить следующий запуск с теми же пределами. |
| Ошибка cleanup или несовпадение SHA при повторной проверке | Проверить шаг остановки и привязку четырёх входных SHA к выбранной попытке. | Закрыть ресурсы только этой попытки. При утрате приватных материалов воспроизвести весь workflow из исходного SHA в новой попытке. |

В публичном отчёте достаточно SHA, времени, кодов ответа и результатов проверки. Первичный пакет с журналом, тела HTTP и содержимое хранилищ остаются на одноразовом runner.

## Сквозная проверка предложения от подготовки до восстановления

M19 использует исходные предложение, данные и доверенные ключи для проверки четырёх экземпляров. Подготовка создаёт дополнительные сценарии отдельно и проверяет сохранность исходных файлов. После очистки runner заново проверяет отчёты M16, M17 и M19. [Порядок захвата и сверки M19](asset-graph-troubleshooting.md).

Сборщик сохраняет полный список хешей приёмки в `evidence/delivery-candidate.json`. Следующий шаг получает его SHA-256 из результата предыдущего шага и вызывает M18. Для этого частичного набора ожидается `inconclusive` и код 2. Runner сверяет, что проверены все отчёты этого запуска, а список отсутствующих совпадает с оставшимися обязательными gates. Подмена отчёта завершает задание ошибкой. [Полная и частичная приёмка M18](final-evidence.md).

В одноразовом GitHub Actions runner M01 проверяет закреплённые версии инструментов, запущенные образы, пространство имён Kubernetes и повторный запуск bootstrap. При несовпадении образа или версии проверьте источник, закреплённый в workflow и конфигурации кластера. В итоговой сверке M01 связана с обучением через тот же checkout, политику и идентификатор worker image.

M10 использует четыре SHA-256, которые runner зафиксировал до обращения к механизму продвижения. Они закрепляют подписанное предложение, запись обучения и оценки, доверенные открытые ключи и исходную политику доверия. Для исходного предложения без подписанного решения ожидается отказ release_assurance_required, два события аудита и прежняя последовательность в хранилище. Положительный переход и повтор того же запроса проверяются на отдельном разрешённом контрольном выпуске. При отказе сверки проверьте идентификатор предложения и хеш исходного отчёта в этой же попытке. [Запуск и диагностика M10](../promotion-entrypoint.md).

M12 получает `M12_PROPOSAL_SHA256` от шага фиксации. Она загружает исходное предложение, наблюдает отказ в допуске, затем запускает HTTP-инференс с лабораторным разрешением и проверяет прогнозы, привязку ответа к модели и отзыв допуска. Обычная командная строка проверяется с отдельным подписанным контрольным выпуском. При `kube_promotion_proposal_pin` сравните файл предложения с хешем в текущей попытке. Очистка проверяет принадлежность кластера и его отсутствие после удаления.

После фиксации предложения M06 выполняет три новых обучения и три отдельных изменения входов (seed, данные, окружение). MLflow сохраняет шесть записей, учётная запись читателя проверяет их повторно. M06 загружает исходные байты ONNX и подписанную оценку из SQL. По идентификатору исходного запроса, порядку строк и признакам эталонной выборки gate воспроизводит ровно тот запрос, который выполнил оценщик. Проверяются хеш запроса и всего ответа, включая порядок отдельных прогнозов. Вероятности и AUPRC сравниваются с каждым из трёх новых обучений. Пределы отклонения составляют `1e-6` и `1e-4` соответственно. Подписанные манифесты независимых рабочих областей имеют разные удостоверения источника. Для сравнения сверяются реальные хеши всех частей набора, входа обучения, окружения и выборки.

При отказе M06 проверьте идентификаторы из отчёта M07 и SHA-256 файла `storage-demo.json`, переданный шагом фиксации. `M06_evaluator_request_mismatch` указывает на отличие признаков, модели или порядка строк. `M06_evaluator_response_mismatch` означает, что результат повторного запроса отличается от подписанного. При `M06_actual_repeat_tolerance` проверьте версии библиотек, входы и сохранённые векторы. Файлы с прогнозами и ключи остаются в одноразовой среде. Учётные данные MLflow не включаются в отчёт. Шаг остановки проверяет оба контейнера tracking-сервиса.

До обучения M02 повторно генерирует исходные данные по `data.lock`, проверяет карантин, подписи и отказ при подмене файлов. M07 независимо считывает три части датасета из SQL и вычисляет SHA-256 канонических строк в порядке train, validation, holdout. Дайджест должен совпасть с подписанной ссылкой на исходные данные в карантине. После восстановления сверка сопоставляет этот дайджест с M02 и с закреплённым в checkout `data.lock`. У исходного набора ещё нет идентификатора кандидата. Связь устанавливается по байтам данных, прочитанным для принятой оценки.

В совместном запуске M07 начинает отсчёт свежести и запускает M03. M03 проверяет неизменность набора данных и разграничение доступа в SQL. Во время единственного обучения M03 записывает, к каким таблицам обращались publisher и scorer, проверяет подпись оценки, отказ при подмене байта модели и повторное чтение исходных артефактов. M07 сверяет образ, набор данных, кандидата и оценку с отчётом M03, затем проверяет качество и лимит обращений к финальной контрольной выборке. При отказе M03 первым проверьте файл .runtime/evidence/M03.json, в том числе поле residual_risks. В этом workflow оператор передаёт `M07_FRESH_WORKSPACE_ID` из подтверждённого bootstrap. M07 принимает только указанное пустое хранилище без предыдущей записи обучения. Проверка бюджета запросов и перезапуска использует отдельный PostgreSQL. Контролируемые недействительные подписи, созданные отрицательными проверками M07, остаются записями в лабораторной базе. Последующие этапы читают исходную подписанную оценку по её идентификатору. После M07 источник доступен следующим шагам до управляемого отключения в M17 или общего шага очистки. При обычном автономном запуске M07 сам создаёт и останавливает своё хранилище.

После фиксации предложения штатные M08 и M09 проверяют устойчивость к отравлению, формат ONNX и поведение при изменении входных признаков. Проверяемый кандидат обучается один раз. Матрица атак обучает свои контрольные и отравленные модели отдельно. Затем выполняются [canary и откат](canary-rollout.md), ежедневная копия и восстановление. При отказе любой обязательной проверки workflow переходит к очистке.

После остановки хранилищ обычные M16 и M17 проверяют первичные результаты. [Сверка отчётов](../../scripts/delivery_candidate.py) читает неизменные входы первоначального предложения: источник, образ, модель, ссылку на оценку и обученный кандидат. Для M07 сверяется также исходный датасет, для всех трёх проверок модели - исходный вход обучения, для runtime-проверок - subject и SHA-256 файла предложения. В строке с `reports` публикуются хеши всех выполненных проверок, `candidate` идентифицирует общий объект проверки. При отказе сверки сравните соответствующие поля отчёта с исходным предложением и записью обучения этой попытки.

Предложение зафиксировано в 03:08:21 UTC. При создании лабораторного разрешения остаток срока оказался меньше обязательных 240 с. M12 завершилась отказом `candidate_inference_window`. Очистка исходного SQL и кластера прошла. При разборе сверить время выпуска исходного предложения с фазой `actual-candidate-bind-proposal` и местом ошибки в журнале. Для повторной проверки нужно выделить время на реальный запуск кандидата и проверить его исходные идентификаторы. [Журнал общего запуска](https://github.com/Abrakadabra124/trusted-mlsecops-platform/actions/runs/43549696772/job/132309044133).

В следующей версии сохраняется проверенная относительная позиция исключения и конечная категория Kubernetes, чтобы установить причину без вывода приватного сообщения. Этот запуск остаётся незавершённым.

Новый сквозной прогон необходим для подтверждения исправления.
