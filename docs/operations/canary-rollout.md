# Поэтапный выпуск и восстановление в лаборатории M16

Workflow [canary-traffic.yml](../../.github/workflows/canary-traffic.yml) выполняется на отдельном Ubuntu runner в GitHub Actions. Его запускает push в ветку проекта при изменении путей, перечисленных в workflow. Запишите SHA коммита, номер запуска и попытки. Все время́нные пороги относятся к одному запуску. Для диагностики используйте номера строк в поле `site`, версии исходников и названия шагов.

## Что измеряется

1. Шаг подготовки получает исходные данные по `data.lock`, обучает CPU-модель, проводит независимую оценку и фиксирует SHA-256 подписанного предложения о выпуске. Обычная авторизация этого предложения требует assurance. Ограниченное разрешение на проверку позволяет отправлять синтетические запросы в изолированном окружении.
2. На два HTTP-сервиса поступает по 200 запросов **суммарно на каждую стадию**. Доля кандидата последовательно составляет 0%, 10%, 50% и 100%. Для каждого успешного ответа сверяются digest модели, digest комплекта и численный прогноз. Переход разрешён при 100 и более валидных наблюдениях, p95 до 200 мс, p99 до 500 мс и приросте ошибок до одного процентного пункта относительно первой стадии.
3. После стадии 100% операторский сценарий отзывает модель в хранилище доверия кандидата. Сценарий фиксирует первый `503 model_unavailable` и отправляет запрос на разрешённую стабильную версию. Измерение заканчивается после получения и проверки её ответа. Счётчик допуска и журнал HTTP позволяют различить отказ до допуска и отказ после регистрации запроса.
4. В отдельной паре временных SQL-хранилищ штатный контроллер последовательно регистрирует два подписанных контрольных выпуска. При отзыве второго выпуска необходим новый подписанный rollback с указанием текущей записи и выбранной записи из истории. Проверка охватывает SQL-состояние, подписи и модель, фактически ответившую через HTTP. Предельное время от начала отзыва до корректного ответа составляет 120 секунд. Попытка вернуться к отозванной версии должна сохранить текущий head. При отсутствии разрешённой модели заявка должна появиться в очереди ручного разбора.
5. После остановки исходного SQL проверяющий читает оба пакета по независимым SHA-256 из outputs предыдущих шагов. Сверяются текущий checkout, образ, исходное предложение, журнал ответов и хронология. Контрольные approvals действуют только в лаборатории. Публикуются агрегаты и контрольные суммы. Сырые запросы, ключи и полномочия SQL остаются на временном runner.

## Действия при отказе

| Наблюдение | Что проверить | Условие продолжения |
| --- | --- | --- |
| `canary-held` | Найдите первую стадию с `passed=false`. Сопоставьте `valid`, `errors`, p95, p99 и результаты сверки модели и прогноза с baseline | Повторить запуск после исправления причины. Сохранить обе ссылки на прогоны |
| Кандидат отвечает после отзыва | Проверить последовательность версий подписанной trust policy, digest отзываемой модели, срок permit и последний успешный ответ кандидата | Получен отказ кандидата и подтверждён ответ разрешённой версии в пределах 120 секунд |
| Откат отказан или выдаёт другой прогноз | Сверить исходный и целевой request SHA, sequence, подпись approver и модель в HTTP-ответе. При отозванной цели использовать ручной разбор | Повторная проверка читает то же разрешённое целое bundle, а журнал содержит новый переход |
| Отказ при replay или очистке | Проверить шаг очистки, владельца SQL, SHA-256 каждого evidence-файла и заново сверить числа запросов с журналом. При перезапуске переисполнить все шаги, создающие исходные пакеты | Для одной попытки совпали все привязки и независимые измерения |

Инструкция по доступу к очереди и восстановлению заявок приведена в [ранбуке ручного разбора](manual-review.md). Решение о производственном выпуске проходит отдельную проверку assurance и approval.
