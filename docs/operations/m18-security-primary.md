# Сохранение исходных доказательств M23 для M18

Ответственный - оператор disposable hosted CI. Процедура сохраняет первичные
материалы уже выполненной M23 и повторно проверяет их после остановки SQL и
удаления кластера. Она не запускает новые эксперименты, не выдаёт разрешение
на выпуск и не заменяет остальные 21 дочерний gate M18.

## Порядок проверки

До первого измерения выполнить на закреплённом чистом checkout:

```sh
python -B -W error -m scripts.m18_security_driver case-inventory
```

Сохранить `expected_cases_sha256` отдельно от будущего отчёта. Перечень строится
из исходного кода проверяющих модулей. Для этой версии это 136 критериев с hash
`ffa626240134a1ac4390c6dad04732983dbe498ff58e57893917f38cac86c22a`.
Четыре критерия outage соответствуют фазам ready, outage, attempt и recover.
Каждый становится pass только после штатной проверки всех подписанных окон
своей фазы. Фактическое количество окон остаётся в `phase_windows` и observations;
ограничения числа окон, доставки и восстановления не изменены. Повреждение
второго окна каждой фазы должно отвергаться даже после пересчёта внешних hashes.

После успешных исходных sources/inventory/outage, transition и проверки
остановленного источника выполнить обычный M23 gate. В `storage-recovery.yml`
он дополнительно требует успешные `stop_sql` и `stop_cluster`. Ошибка более
поздней независимой стадии не запрещает сохранение уже проверенной M23,
но общий workflow при этом остаётся failure.

Для capture и replay нужны внешние значения из той же попытки:

| Переменная | Источник |
| --- | --- |
| `M18_FREEZE_SHA256` | Исходный receipt M18 и четыре frozen file pins |
| `M18_SECURITY_CASES_SHA256` | Результат case-inventory до измерений |
| `M23_RUN_ID`, `M23_RUN_ATTEMPT` | Первоначальный GitHub run и attempt |
| `M23_REPORT_SHA256` | Точные байты исходного успешного M23.json |
| `M23_PROPOSAL_SHA256` | Исходный release-native.json |
| `M23_SOURCES_SHA256`, `M23_INVENTORY_SHA256`, `M23_OUTAGE_SHA256` | Исходные stage manifests |
| `M23_TRANSITION_SHA256` | Receipt удаления прежних mutable authorities |
| `M23_WORKSPACE_SHA256` | SHA-256 первоначального workspace.json, не его UUID |

```sh
python -B -W error -m scripts.m18_security_driver capture
python -B -W error -m scripts.m18_security_driver replay
```

Перед второй командой передать `index_sha256` первой как
`M18_SECURITY_INDEX_SHA256`. Workflow делает это через выход шага. Нельзя
самостоятельно выбирать pins из непроверенного отчёта или использовать run owner
новой попытки вместо первоначального.

Collector проверяет оригинальные 20 artifact references, подписи, source,
candidate/evaluation/model/proposal, исходные stage/owner files и private packets.
Он сохраняет точные preimages в `.runtime/evidence/M18-objects`, включая отдельно
canonical JSON и файл с завершающим LF там, где producer использует разные hashes.
Replay читает объекты по hash, а не текущие каталоги стадий. Общие frozen inputs и
подписанный пакет M18 остаются необходимы. Исходные M23 stage files для replay
больше не нужны. Приватные packets и registry не публикуются.

## Отказ и восстановление

При `M18 security primary verification failed` сначала сверить все внешние pins,
исходный source и owner, затем наличие объектов. Не перезапускать native кампанию
поверх этой попытки и не заменять повреждённый объект новым отчётом.

Если retention прервался, повторить capture с прежними аргументами допустимо:
совпадающие объекты принимаются, отсутствующие сохраняются. Существующий объект с
другими байтами вызывает отказ; автоматического исправления нет. Если исходный
материал утрачен, этой попытки недостаточно для M18. Сохранить диагностический
статус вне публичного репозитория и выполнить новую полноценную попытку отдельно.

Rollback изменения выполняется возвратом source revision и новым запуском.
Исторические отчёты не переписываются под новый перечень критериев. Успешный
replay возвращает `release_ready: false`: итоговую полноту и governance принимает
только [финальная процедура M18](final-evidence.md).

## Проверенное и ещё не проверенное

Локальные тесты проверяют retained replay после удаления исходных M23 файлов,
повреждённые и отсутствующие objects, чужой owner, подмену frozen candidate,
подписей и окон outage. Driver и исходный signed freeze проверены на двух
контролируемых семействах fixtures; их join подменён в тестах, поскольку у них
разные кандидаты. Поэтому эти тесты не доказывают native связывание одного
кандидата. Новому workflow всё ещё требуется такой hosted запуск с cleanup.
